# Web Accessibility

Berkeley websites must meet [WCAG 2.1 AA](https://www.w3.org/TR/WCAG21/) (see Berkeley's
[Digital Accessibility page](https://dap.berkeley.edu/)). The `A11y` workflow checks every page of the
app against it on each push and pull request, as [seating](https://github.com/berkeley-cdss/seating/blob/main/docs/a11y.md)
does, following the approach of [berkeley-class-site](https://github.com/berkeley-cdss/berkeley-class-site/blob/main/docs/a11y.md).

## What the tests do

`tests/a11y/test_a11y_pages.py` seeds a course, starts the app against the [fake Canvas](../README.md#fake-canvas),
and opens every page in headless Chrome, signed in through `/dev_login/` as the kind of user who sees it: a
student, a TA or a teacher. Course pages are the React app, so each a11y audit waits until the page's data has
loaded. On each page it runs [axe-core](https://github.com/dequelabs/axe-core) twice:

- `test_meets_wcag_21_aa` checks the `wcag2a`, `wcag2aa`, `wcag21a` and `wcag21aa` rules. These must pass.
- `test_meets_wcag_22_aa` checks the `wcag22aa`, `best-practice` and `section508` rules. These are marked
  as expected failures for now, so they are reported without failing the build.

An a11y audit also fails if the page didn't load: if it redirected somewhere unexpected, showed an error page,
or the course page couldn't load its data.

`test_every_page_is_audited` fails when a new route is added to the app but not to `PAGES` (or to
`SKIPPED_RULES`, with a reason) in that file. The course pages' client-side routes each have a Flask route
(`server/state.py`), so a new course page needs both.

## Running them

The course pages need the frontend build in `server/static/`, as in the Docker image:

```bash
yarn build && cp -R build/. server/static/
pytest tests/a11y
```

Rebuild after changing the frontend. You need Chrome installed. When a page fails, the test prints each
broken rule with the elements that break it, and the end of the run lists the pages for each rule. The full
axe report for every page is saved in `axe/`, with a screenshot of each failing page in `axe/screenshots/`. In
CI, these are uploaded as the `axe` artifact of a failed run.

## Exceptions

`SKIPPED_RULES` in `tests/a11y/utils.py` turns an axe rule off for every page, and elements marked
`data-a11y-errors="true"` are left out of every rule. Both are a last resort: fix the page if you can, and
keep an exception as small as possible, with a comment saying why.

## What the tests can't check

axe finds roughly a third of WCAG problems. Check these by hand when you change a page:

- Everything works with the keyboard alone, in a sensible order, with a visible focus outline.
- A screen reader (VoiceOver: <kbd>Cmd</kbd>+<kbd>F5</kbd>) announces controls, messages and dialogs sensibly.
- The page still works zoomed to 400% (or at 320px wide) without scrolling sideways.
- The contrast of text axe marks as "incomplete".

The a11y audit opens each page as it first loads. Dialogs (such as adding students or importing a sheet), menus
and the states after an action aren't audited, so check them by hand when you change them.
